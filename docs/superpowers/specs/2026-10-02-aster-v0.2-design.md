# Aster v0.2: Enums and Match (Design)

**Date:** 2026-10-02
**Status:** Approved in brainstorming, pending spec review
**Builds on:** [`2026-10-01-aster-v0.1-design.md`](2026-10-01-aster-v0.1-design.md). Everything in v0 and v0.1 still holds unless this document changes it.

## 1. Purpose

v0.2 is the second of three milestones toward a self-hosted Aster compiler:

| Milestone | Adds |
|-----------|------|
| v0.1 | Structs, growable arrays, compound assignment, `for` loops |
| **v0.2** (this spec) | Enums with positional payloads and an exhaustive `match` |
| v0.3 | File/stdin input and program arguments |

A compiler written in Aster needs tagged unions for token kinds, AST nodes and optional values. v0.2 adds them as enums and gives them a `match` that the compiler checks for exhaustiveness. Because there are still no generics, an optional value is a per-type enum such as `enum NodeOpt { None, Some(Node) }`.

### Success criteria

v0.2 is done when:

1. The `Type` union has gained `{ kind: 'enum' }`, and the existing golden suite and unit tests pass unchanged.
2. The golden suite covers every feature in §3, including every new compile error.
3. Two new "real program" golden tests pass:
   - `programs/calc.aster` is an arithmetic expression calculator. It has a tokenizer over a payload-free `Kind` enum, a recursive-descent parser that builds an `Expr` AST enum, and an evaluator written with `match`. It prints results for a handful of fixed input strings, covering precedence, parentheses and unary minus.
   - `programs/bst.aster` is a binary search tree over `enum Tree { Leaf, Node(Tree, int, Tree) }`. It does insert, contains, and an in-order traversal into `[int]`.
4. `docs/spec/language.md` and `README.md` describe v0.2.

### Non-goals for v0.2

Nested patterns, matching on `int`/`bool`/`string` values, match guards, named-field variants, generics, a "never" type, equality on enums with payloads, printing enums, methods, null, I/O beyond `print`, freeing memory, and an LLVM backend.

## 2. Semantics decisions (summary)

- **Variants carry zero or more positional values.** Named data goes in a struct used as a payload.
- **Variants are always qualified with `::`** (`Expr::Num(1)`). The parser recognises a variant from the syntax alone, so variants never collide with locals, fields or other enums.
- **Payload-free enums are values; all other enums are references.** If no variant of an enum carries a payload, its values are plain integer tags. Otherwise its values are heap-allocated references, like structs, and nothing is freed.
- **`==`/`!=` work only on payload-free enums.** They compare variants.
- **`match` is exhaustive and has no dead arms.** A missing variant and an unreachable arm are both compile errors. The language has no warnings.

## 3. Language changes

### 3.1 Lexical

- New keywords: `enum`, `match`.
- New punctuation: `::`, `=>`.
- `_` on its own is a new token. It is no longer an identifier, so it cannot name a variable, function, type, field or variant. Identifiers that start with `_` (`_x`, `__`) are unaffected.
- Maximal munch: `::` and `=>` are single tokens. A lone `:` and a lone `=` lex as before.

### 3.2 Types

| Type | Meaning |
|------|---------|
| `Name` | A value of the enum `Name`: an integer tag if the enum is payload-free, otherwise a reference to a heap object. |

Enum type equality is nominal. An enum is **payload-free** when none of its variants declares a payload. That is a property of the declaration, and it does not create a separate kind of type.

### 3.3 Grammar

This shows only the rules that change or are new relative to v0.1 §3.3. Everything else is unchanged.

```
item        = function | structDecl | enumDecl ;
enumDecl    = "enum" IDENT "{" variant { "," variant } [ "," ] "}" ;
variant     = IDENT [ "(" type { "," type } ")" ] ;

statement   = …                       (all v0.1 forms)
            | matchStmt ;
matchStmt   = "match" expr "{" { pattern "=>" ( block [ "," ] | expr "," ) } "}" ;

primary     = …                       (all v0.1 forms)
            | variantExpr
            | matchExpr ;
variantExpr = IDENT "::" IDENT [ "(" expr { "," expr } ")" ] ;
matchExpr   = "match" expr "{" pattern "=>" expr { "," pattern "=>" expr } [ "," ] "}" ;

pattern     = "_" | IDENT "::" IDENT [ "(" binder { "," binder } ")" ] ;
binder      = IDENT | "_" ;
```

Notes:
- **Statement or expression.** A statement that begins with `match` is always a `matchStmt`, mirroring `if`. A `match` anywhere else (an initialiser, an argument, an operand, after `return`) is a `matchExpr`.
- **`matchStmt` arms.** An arm body is either a block, optionally followed by `,`, or an expression followed by `,`. The comma after the final expression arm may be omitted. A `matchStmt` may have zero arms syntactically; the checker then reports it as non-exhaustive.
- **`matchExpr` arms.** Each arm body is a single expression, and arms are separated by commas. There must be at least one arm, and a trailing comma is allowed.
- **Scrutinee.** The expression after `match` is parsed in v0.1's no-struct-literal mode, so `match p {` starts the arms.
- **Enum declarations.** An enum needs at least one variant: `enum E {}` is a parse error. Empty payload parentheses (`V()`) are a parse error, in a declaration, an expression or a pattern. Payload lists, argument lists and binder lists do not allow trailing commas. The variant list does.
- **Precedence.** `variantExpr` and `matchExpr` are primaries. `Expr::Num(1).x` parses as a field access on the variant expression, which then fails type checking.
- **Patterns are flat.** A pattern is `_` or a variant with one binder per payload slot. Nested patterns are a non-goal.

### 3.4 Declarations and name resolution

- Enums are top-level items and may appear in any order relative to functions and structs. Enums and structs may refer to themselves and to each other.
- Enum names live in the type namespace with struct names. An enum name must not be `int`, `bool`, `string` or `void`, and must not duplicate another struct, enum, function or builtin.
- A local variable may share an enum's name. `E::V` always resolves `E` in the type namespace.
- Variant names must be unique within their enum (`duplicate variant '<V>' in '<E>'`). Any identifier is allowed, and the same variant name may appear in different enums.
- Each payload type must resolve and must not be `void`.
- Each variant's **tag** is its index in declaration order, starting at 0.

### 3.5 Type rules

**Variant construction** `E::V` or `E::V(e1, …, en)`
- If no type is called `E`, the error is `unknown enum '<E>'`. If `E` is a struct or a primitive type, the error is `'<E>' is not an enum`.
- `V` must be a variant of `E` (`unknown variant '<V>' on '<E>'`).
- The number of values must equal the variant's arity (`variant '<E>::<V>' expects <N> values, got <M>`). This covers both writing `E::V` for a payload variant and passing values to a unit variant.
- Each `ei` is checked with the payload slot's type as its **expected type** (v0.1 §3.5), so `Opt::Some([])` infers. Values are evaluated left to right.
- The result has type `E`.

**`match`** (both forms)
- The scrutinee must have an enum type (`cannot match on '<T>' values`). It is evaluated exactly once, before any arm is chosen.
- A variant pattern `F::V(...)` follows the construction rules for resolving `F` and `V`. `F` must also be the scrutinee's enum (`pattern type '<F>' does not match '<E>'`).
- The binder count must equal the variant's arity, using the same `expects <N> values, got <M>` message.
- Binder names must be unique within one pattern (`duplicate binding '<x>'`).
- Each binder is a new immutable binding scoped to its arm, typed as its payload slot, and may shadow outer names. `_` binds nothing.
- **Exhaustiveness.** Every variant must be covered by a variant arm, or there must be a `_` arm. Otherwise the error is `non-exhaustive match: missing '<E>::<A>', '<E>::<C>'`, listing every uncovered variant in declaration order. It is reported at the `match` keyword.
- **Reachability.** It is the error `unreachable match arm`, reported at that arm's pattern, when:
  - a variant appears in an earlier arm too
  - any arm follows a `_` arm
  - a `_` arm comes after every variant is already covered
- Arms are checked in order, so each problem is reported once.

**`matchExpr`**
- All arm bodies must have the same type, which is the type of the `match`. That type must not be `void`.
- An expected type flows into every arm body, as it does into `if` expression branches. v0.1 §3.5 gains this position.
- As with `if` expressions, `panic(...)` cannot be an arm body, because it has type `void`.

**`matchStmt`**
- Arm bodies may be any statement-level block or expression. Expression values are discarded.
- **Return analysis.** A `matchStmt` terminates a control path exactly when every one of its arms terminates it. Since every match is exhaustive, this is sound.
- `break` and `continue` inside an arm refer to the nearest enclosing loop, as in any block.

**Equality**
- `==` and `!=` on two values of the same payload-free enum compare their variants.
- On any other enum the error is `cannot compare '<E>' values`.

**`print`** still accepts only `int`, `bool` and `string`.

**Error cascades.** An `error`-typed scrutinee suppresses the pattern, exhaustiveness and reachability diagnostics for that `match`. Its arm bodies are still checked, with binders typed `error`.

### 3.6 Runtime

There are no new panics, because exhaustiveness makes a failed match impossible. Allocating a value of a payload enum can fail with the existing `out of memory` panic.

### 3.7 Example

```
enum Expr { Num(int), Add(Expr, Expr), Neg(Expr) }
enum Kind { Plus, Minus, Eof }

fn eval(e: Expr): int {
    return match e {
        Expr::Num(n) => n,
        Expr::Add(a, b) => eval(a) + eval(b),
        Expr::Neg(x) => -eval(x),
    };
}

fn main(): int {
    let k: Kind = Kind::Plus;
    if k == Kind::Plus {
        print(eval(Expr::Add(Expr::Num(2), Expr::Neg(Expr::Num(5)))));   // -3
    }
    return 0;
}
```

## 4. Compiler changes

### 4.1 Types (lands first, behaviour-preserving)

`Type` in `types/type.ts` gains `{ kind: 'enum'; name: string }`.
- `typeEquals` compares names.
- `typeToString` prints the bare name.

Every exhaustive `switch` over `Type['kind']` gets an `enum` case. Where no enum can reach that switch yet, the case throws an internal error. No syntax is added, and the full v0.1 suite must pass unchanged.

### 4.2 Lexer, AST and parser

**Lexer:** the keywords and tokens from §3.1.

**AST additions:**
- `Program.items` gains `enumDecl`: `{ name; variants: { name; payload: TypeExpr[]; span }[] }`.
- A `variant` expression: `{ enumName; variant; args: Expr[] }`.
- A `match` expression and a `match` statement, each `{ scrutinee; arms: { pattern; body }[] }`. A statement arm's body is a block or an expression.
- `Pattern = { kind: 'wildcard' } | { kind: 'variant'; enumName; variant; binders: (Binder | null)[] }`. Each `Binder` carries a name and a span, and `null` stands for `_`.
- The s-expression printer learns every new node.

**Parser:**
- In `primary`, an `IDENT` followed by `::` starts a `variantExpr`, and the `match` keyword starts a `matchExpr`.
- In statement position, `match` starts a `matchStmt`.
- The scrutinee is parsed with `noStructLit` set.
- Error recovery also synchronises at `enum` and `match`.

### 4.3 Checker

- **Pass 1** collects enums together with structs and function signatures. It handles the type namespace, collisions, duplicate variants and payload type resolution, and builds each enum's variant table: name, tag, payload types, plus the `payloadFree` flag.
- **Pass 2** checks the `variant` and `match` expressions and the `match` statement (§3.5).
  - Exhaustiveness and reachability use one `Set<tag>` per match plus a `wildcardSeen` flag. Patterns are flat, so this is linear and needs no pattern matrix.
  - Return analysis gains the `matchStmt` rule from §3.5.
- **Typed tree:**
  - `TypedProgram` gains `enums: { name; payloadFree; variants: { name; tag; payload: Type[] }[] }[]`.
  - A typed `variant` expression carries the enum name and the tag.
  - Each typed arm carries `tag | 'wildcard'` and a binder local for every slot that isn't `_`.
  - Enum `==`/`!=` is recorded as a distinct binary form, so lowering doesn't need to look at the operand types again.

### 4.4 IR and lowering

`IrProgram` gains `enums` with the same shape as the typed `enums`. These are new:

| Instruction | Meaning |
|-------------|---------|
| `enum_new dst, Enum, tag, [operands]` | Build a variant value. Lowering has already evaluated the operands, left to right, into temporaries. |
| `enum_tag dst, value` | Read the tag as an `int`. |
| `enum_field dst, value, Enum, tag, i` | Read payload slot `i`. Valid only where the value's tag is known to be `tag`. |

| Terminator | Meaning |
|------------|---------|
| `switch value, [tag → label]…, default` | Multi-way branch on an `int`. `default` is a label, or `unreachable` when no other value can occur. |

Lowering:
- **Enum equality.** Emit `enum_tag` on each operand, then the ordinary int `eq`/`ne`. Backends never compare enums directly.
- **`match`.**
  - Evaluate the scrutinee into a temporary `s`, then `t = enum_tag s`, then `switch t`.
  - Each variant arm gets its own block. The block starts with `enum_field` for each binder that isn't `_`, runs the arm body, and then jumps to `join`.
  - The `_` arm is the `default` target. With no `_` arm, the default is `unreachable`.
  - `matchExpr` stores each arm's value into one result temporary, as `ifExpr` does.
  - An arm whose body terminates doesn't jump to `join`. If no arm reaches `join`, `join`'s terminator is `unreachable`, following the existing `if` handling.

The IR printer prints the new instructions and `switch`.

### 4.5 C backend

**Mangling** (added to v0.1 §4.5):
- An enum `E` becomes the C type `aster_E_E`.
- A variant `V` becomes the union member `v_V`.
- Payload slot `i` becomes `p<i>`.

**Payload-free enums**
- The C type is `int64_t`, and no declaration is emitted.
- `enum_new` emits `dst = INT64_C(tag);`, and `enum_tag` emits a plain copy.
- The zero value of locals is `0`.

**Other enums.** These are emitted like structs, with every struct and enum typedef before any definition:
```c
typedef struct aster_E_Expr *aster_E_Expr;
struct aster_E_Expr {
    int64_t tag;
    union {
        struct { int64_t p0; } v_Num;
        struct { aster_E_Expr p0; aster_E_Expr p1; } v_Add;
        struct { aster_E_Expr p0; } v_Neg;
    } u;
};
```
- Only variants with payloads become union members.
- The union is never empty, because an enum with no payloads is payload-free and takes the path above.
- `enum_new` emits `aster_rt_alloc(sizeof(struct aster_E_E))`, then the tag store and the payload stores. Unit variants of these enums allocate too.
- `enum_tag` emits `value->tag`, and `enum_field` emits `value->u.v_V.p<i>`.
- The zero value of locals is `NULL`.

`cType` and `zeroValue` need the enum table to tell the two cases apart, so the emitter builds a name → enum map once per program.

**`switch`** is emitted as:
```c
switch (l3) { case 0: goto L4; case 2: goto L5; default: goto L6; }
```
With an `unreachable` default, the last case becomes `default: aster_rt_unreachable();`. The scrutinee is an `int64_t`, so `-Wswitch` has nothing to say, and the output stays clean under `-std=c11 -Wall -Werror`.

The runtime does not change.

### 4.6 Unchanged

These are unchanged:
- diagnostic formatting
- the cc invocation
- the CLI commands and exit codes
- the golden-test directive format

`--emit=tokens|ast|ir|c` shows the new constructs.

## 5. Testing

### 5.1 Golden programs

New feature folders under `tests/programs/`:

- `enums/`
  - unit, single-payload and multi-payload variants
  - left-to-right evaluation of payload values, shown with prints
  - `[]` inferred as a payload value
  - a recursive enum
  - an enum and a struct that refer to each other: a linked list via `enum NodeOpt { None, Some(Node) }`
  - an enum declared after its use
  - enums as fields, array elements, parameters and return values
  - aliasing: a struct inside a payload is shared, not copied
  - `==`/`!=` on a payload-free enum
- `match/`
  - statement form with block arms and expression arms
  - expression form, nested, as a call argument and after `return`
  - binders, `_` binders, and binders that shadow outer names
  - a `_` arm, alone and after some variants
  - the scrutinee evaluated once, shown with a side effect
  - `break`/`continue` from arms inside a loop
  - a non-`void` function whose only `return`s are inside `match` arms
  - a match on a payload-free enum

Additions to `errors/`:
- unknown enum, `'E' is not an enum`, unknown variant
- wrong arity: on construction, on a pattern, `E::V` for a payload variant, and values passed to a unit variant
- a duplicate variant
- an enum colliding with a struct, a function, a builtin and a primitive type
- a `void` payload
- `cannot match on 'int' values`
- a pattern of the wrong enum
- a duplicate binder
- `non-exhaustive match` with several missing variants listed in order
- each of the three `unreachable match arm` cases
- mismatched `matchExpr` arm types, and a `void` arm
- `cannot compare` on a payload enum
- `print` of an enum
- `_` used as a variable name
- parse errors: `enum E {}`, `V()`, and a struct literal as an unparenthesised scrutinee
- a missing return when one `matchStmt` arm falls through

No new `panics/` (§3.6).

Real programs, in `programs/`: `calc.aster` and `bst.aster` (§1).

### 5.2 Unit tests

These stay lean, as in v0.1:
- **Lexer:** `::`, `=>` and `_`, plus `_x` and `__` still lexing as identifiers.
- **Parser snapshots:**
  - enum declarations
  - variant expressions with and without values
  - both `match` forms, and the two arm styles in statements
  - the scrutinee in no-struct-literal mode
  - recovery at `enum`
- **Checker:**
  - exhaustiveness and reachability on a small table of cases
  - return analysis through `matchStmt`
  - expected types flowing into payload values and `matchExpr` arms
- **Lowering snapshots:**
  - a `match` with binders, `_` binders and a `_` arm
  - a `matchExpr` result temporary
  - enum equality lowered via `enum_tag`
- **Emitter:**
  - the typedef and union layout for a recursive enum that refers to a struct and back
  - the payload-free `int64_t` path
  - `switch` with a label default and with an `unreachable` default

### 5.3 Workflow

As in v0.1:
- TDD, with a failing golden program or unit test first.
- Conventional commits.
- CI runs typecheck, lint and test.

The §4.1 type change comes first and must change no tests.

## 6. Looking ahead (informing, not in scope)

- **v0.3** adds reading files and stdin into `string`, and program arguments as `[string]`. With `calc.aster` in place, a v0.3 program can tokenise and parse a real source file.
- **Later:**
  - Nested patterns and a never type would make a self-hosted compiler more pleasant to write. Generics would replace per-type optionals.
  - The `switch` terminator and the tagged-union layout map directly onto LLVM's `switch` and a `{ i64, [N x i8] }`-style struct.
