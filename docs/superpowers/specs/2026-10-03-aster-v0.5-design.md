# Aster v0.5: Generic Enums and `?` (Design)

**Date:** 2026-10-03
**Status:** Approved in brainstorming
**Builds on:** [`2026-10-03-aster-v0.4-design.md`](2026-10-03-aster-v0.4-design.md). Everything in v0–v0.4 still holds unless this document changes it.

## 1. Purpose

The two costliest remaining friction-log items ([`docs/self-host/friction.md`](../../self-host/friction.md)) are shortlist items 1 and 3:

| Shortlist item | Friction entries | v0.5 feature |
|----------------|------------------|--------------|
| 1. Error propagation | 1 | the postfix `?` operator on `Option` and `Result` |
| 3. Generic enums | 3 | user-declared generic enums, with `Option[T]` and `Result[T, E]` predeclared |

`parse.aster` has 100 `if p.failed { return bad_*(); }` checks, six `bad_*()` placeholder constructors and two hand-written
`Maybe*` enums. v0.5 makes all of them unnecessary, and the milestone proves it by deleting them.

### Success criteria

v0.5 is done when:

1. The golden suite covers every feature in §3, including every new compile error.
2. `lex.aster` and `parse.aster` lex and parse all v0.5 syntax, and `tests/lex_aster.test.ts` and
   `tests/parse_aster.test.ts` pass over the whole corpus, including new golden programs and fixtures.
3. `parse.aster` is rewritten to use the new features (§5):
   - parse functions return `Option[X]` and propagate failure with `?`
   - the `failed` field and every `if p.failed` check are gone
   - all six `bad_*()` constructors are gone
   - `MaybeType` and `MaybeExpr` are replaced by `Option[TypeExpr]` and `Option[Expr]`
   - both `lex.aster` and `parse.aster` read their input through `read_file`'s `Result`
4. `docs/spec/language.md`, `README.md` and `docs/self-host/friction.md` describe v0.5. The friction log marks entries
   1 and 3 as resolved, with before and after counts.

### Non-goals for v0.5

Generic structs, generic functions, explicit type arguments in expressions (no turbofish), conversion of error types
in `?`, methods (`unwrap_or` and similar), `?` on anything other than `Option` and `Result`, type aliases, and modules.

## 2. Semantics decisions (summary)

- **Enums may take type parameters:** `enum Tree[T] { Node(T, [Tree[T]]), Leaf }`. Structs and functions may not.
- **`Option` and `Result` are predeclared**, as if every program declared
  `enum Option[T] { Some(T), None }` and `enum Result[T, E] { Ok(T), Err(E) }`.
- **`ReadResult` is removed.** `read_file` returns `Result[string, string]`. This is a breaking change, made because the
  language is pre-1.0 and only the corpus uses `ReadResult`.
- **Type arguments are never written in expressions or patterns.** A variant expression takes them from the type its
  context expects, or else infers them from its payload values. Patterns take them from the scrutinee.
- **`e?`** unwraps `Option::Some`/`Result::Ok` or returns `Option::None`/`Result::Err(e)` from the enclosing function. The
  function must return the same kind, and for `Result` the error type must be identical.
- **Generic enums are monomorphised in the checker.** Each distinct instantiation (`Option[int]`, `Option[Expr]`)
  becomes an ordinary enum in the typed program, so lowering and C emission treat it like any other enum.

## 3. Language changes

### 3.1 Lexical

`?` is a new single-character punctuator. No keywords are added; `Option` and `Result` are predeclared type names, not
keywords.

### 3.2 Grammar

```
enumDecl    = "enum" IDENT [ typeParams ] "{" variant { "," variant } [ "," ] "}" ;
typeParams  = "[" IDENT { "," IDENT } "]" ;
type        = IDENT [ "[" type { "," type } "]" ] | "[" type "]" ;
postfix     = primary { "(" [ expr { "," expr } ] ")" | "." IDENT | "[" expr "]" | "?" } ;
```

- A type parameter list has at least one name: `enum E[] { … }` is `expected identifier, found ']'`. A type argument
  list has at least one type: `Option[]` is `expected identifier, found ']'`.
- Trailing commas are not allowed in type parameter lists or type argument lists.
- In type position `Name[` always starts a type argument list, so array types and type arguments never conflict.
- `?` binds like the other postfix operators: `-x?` is `-(x?)`, `a.b?` is `(a.b)?`, and `f(x)?.y` and `xs[0]?` work. `?`
  may repeat (`x??`).

### 3.3 Generic enum declarations

- Type parameter names must be distinct (`duplicate type parameter 'T'`).
- A type parameter must not be named `int`, `bool`, `string` or `void`, or share a name with a struct, an enum
  (including `Option` and `Result`), or a builtin function: `type parameter 'T' conflicts with a type of the same name`.
  This is reported once per offending parameter.
- Inside its enum's variant list, a type parameter can be used wherever a type can: alone, as an array element or as
  a type argument. Outside its enum it is unknown (`unknown type 'T'`). A type parameter cannot take arguments
  (`'T' is not generic`).
- Every type parameter must appear in at least one payload type: `type parameter 'T' is never used`. A generic enum
  therefore always has a payload, so it is always a heap-allocated reference.
- **Infinite expansion.** A set of generic enums that would need infinitely many instantiations is rejected at the
  declaration, whether or not the enum is used: `generic enum 'E' expands infinitely`. Concretely, build a graph whose
  nodes are the (enum, parameter) pairs. For each type argument `A` passed to parameter `Q` of enum `F` inside a payload
  of enum `E`, and each parameter `P` of `E` that occurs in `A`, add an edge `(E, P) → (F, Q)`. The edge is *expanding*
  when `A` is not exactly `P`. Each enum that has a parameter on a cycle containing an expanding edge is reported once,
  at its name. Regular recursion such as `enum List[T] { Cons(T, List[T]), Nil }` is fine, and `enum Bad[T] {
  B(Bad[[T]]) }` is rejected.
- Errors in a generic enum's declaration (unknown types, `void` payloads, arity mistakes) are reported once, at the
  declaration, whether or not the enum is used.
- `Option` and `Result` cannot be redefined: `'Option' is a builtin type and cannot be redefined`. As before, no type
  may share a name with a builtin function.

### 3.4 Types

- `Name[T1, …]` names an instantiation of a generic enum. The argument count must equal the parameter count:
  `'Option' expects 1 type argument, got 2` and `'Result' expects 2 type arguments, got 1`. A generic enum written with
  no arguments is the same error with `got 0`. Arguments on a non-generic type are `'Point' is not generic` (also for
  `int` and the other primitives).
- Type arguments may be any type except `void` (`type argument cannot be void`), including arrays, structs and other
  instantiations.
- Two instantiations are equal when their enum names are equal and their arguments are pairwise equal.
- Diagnostics write instantiations as `Option[int]` and `Result[[string], string]`, with `, ` between arguments.
- An instantiation follows the rules of a non-generic enum with its type arguments substituted into its payloads. It
  is not payload-free, so `==`, `!=`, `print` and `eprint` reject it, as they do any enum with payloads.

### 3.5 Variant expressions and inference

`E::V(e1, …)` where `E` is generic infers `E`'s type arguments:

1. **From context.** If the expression appears where a type is expected, and that type is an instantiation of `E`, its
   arguments are used. The contexts are the ones that already type an empty `[]`: a `let`/`var` type, an assignment
   target, a function argument, a `return` value, a struct literal field, a variant payload value, `push`'s second
   argument, an array literal element, and an `if`/`match` expression arm in one of those positions. An expected
   type that is not an instantiation of `E` is ignored here and reported as an ordinary mismatch afterwards.
2. **From payload values.** Otherwise the values are checked left to right. Each value takes its slot type as context
   if the parameters it mentions are already known. Then its type is matched against the slot type, which fixes any
   parameter that was still unknown. A later value whose slot mentions a parameter fixed earlier is checked against
   that type (`Pair::P(1, true)` with `P(T, T)` is `type mismatch: expected int, found bool`).
3. If any parameter is still unknown, the error is `cannot infer type arguments for 'E'`, at the variant expression,
   and the expression's type is the error type.

So `Option::Some(5)` works anywhere, `Option::None` and `Result::Ok(1)` need context, and `let x: Option[[int]] =
Option::Some([]);` works because the context fixes `T` before the payload is checked.

Errors that don't involve generics (`unknown enum`, `unknown variant`, the payload count) are unchanged.

### 3.6 Patterns

Variant patterns never carry type arguments: `Option::Some(x)` matches any `Option` instantiation. Binder types are the
scrutinee instantiation's payload types. Exhaustiveness and reachability work by variant, as before. A variant pattern
naming a different enum than the scrutinee is reported as before, with the pattern's type written as the bare enum
name: `pattern type 'Result' does not match 'Option[int]'`.

### 3.7 The `?` operator

`e?` evaluates `e` once.

| `e`'s type | Enclosing function must return | Value of `e?` | When `e` is the failure variant |
|------------|-------------------------------|---------------|-------------------------------|
| `Option[T]` | `Option[U]` for any `U` | the `Some` payload, of type `T` | returns `Option::None` |
| `Result[T, E]` | `Result[U, E]` for any `U`, with the same `E` | the `Ok` payload, of type `T` | returns `Result::Err(x)`, where `x` is the `Err` payload |

Errors, at the `?` expression:
- `'?' applies to Option or Result, not 'X'` when `e` has any other type.
- `'?' needs the function to return an Option, but it returns 'X'` (or `a Result`) when the return type is the wrong
  kind, including `void` and `int` (so `?` cannot be used in `main`).
- `'?' error type 'E1' does not match the function's error type 'E2'` when both are `Result` with different error
  types. There is no implicit conversion.

If `e` has the error type, no further error is reported and `e?` has the error type. `?` does not end a control path
for the missing-return analysis.

### 3.8 Builtins

`read_file(path: string): Result[string, string]`, with the same behaviour as v0.4: `Ok(contents)` or
`Err("<path>: <reason>")`.

### 3.9 Example

```aster
enum Tree[T] { Node(Tree[T], T, Tree[T]), Leaf }

fn parse_digit(s: string, i: int): Option[int] {
    if i >= len(s) {
        return Option::None;
    }
    let b: int = byte_at(s, i);
    if b < '0' || b > '9' {
        return Option::None;
    }
    return Option::Some(b - '0');
}

fn sum2(s: string): Option[int] {
    return Option::Some(parse_digit(s, 0)? + parse_digit(s, 1)?);
}

fn load(path: string): Result[int, string] {
    let text: string = read_file(path)?;
    return Result::Ok(len(text));
}

fn total(t: Tree[int]): int {
    return match t {
        Tree::Node(l, v, r) => total(l) + v + total(r),
        Tree::Leaf => 0,
    };
}

fn main(): int {
    match sum2("42") {
        Option::Some(n) => print(n),   // 6
        Option::None => print("bad"),
    }
    let leaf: Tree[int] = Tree::Leaf;
    print(total(Tree::Node(leaf, 5, Tree::Node(leaf, 7, leaf))));   // 12
    match load("/nonexistent") {
        Result::Ok(n) => print(n),
        Result::Err(e) => eprint(e),
    }
    return 0;
}
```

## 4. Compiler changes

### 4.1 Lexer and tokens

`?` joins the single-character punctuators.

### 4.2 AST and parser

- `TypeExpr`'s `named` case gains `args: TypeExpr[]`, empty when there are no brackets. Its span runs to the closing
  `]`.
- `EnumDecl` gains `typeParams: { name: string; nameSpan: Span }[]`.
- `Expr` gains `{ kind: 'try'; operand: Expr; span: Span }`, spanning the operand to the `?`.
- `sexpr` renders `try` as `(? e)`.

### 4.3 Checker

- **Representation.** The enum case of `Type` gains `args: Type[]`, empty for a non-generic enum. `typeEquals` compares
  names and arguments, and `typeToString` prints `Name[a, b]`.
- **Templates and instantiations.** Collection registers every type name first, then each generic enum's parameters,
  then runs the expansion check (§3.3), and only then resolves payloads. A generic enum is kept as a template: its
  payload `TypeExpr`s with its parameter names. The template's payloads are resolved once with each parameter bound to
  a placeholder, only to report declaration errors. Instantiating `E[args]` resolves the template's payloads with
  parameters bound to `args`. Each instantiation is memoised by its type string, and it is registered before its
  payloads are resolved so recursive enums terminate. The expansion check guarantees there are finitely many.
- **Typed program.** `TypedProgram.enums` holds the non-generic user enums in declaration order, followed by the
  instantiations the program uses, in order of first use. An instantiation's `TEnum.name` is its type string
  (`Option[int]`), and enum-typed values refer to it by that name. Unused instantiations and unused generic enums
  produce nothing, just as an unused `ReadResult` produced nothing before.
- **Inference** follows §3.5 and works on the template's payload `TypeExpr`s and a map of parameter bindings.
- **`?`** checks to a new typed expression
  `{ kind: 'try'; type: Type; operand: TExpr; okTag: number; failTag: number; returnEnum: string; returnFailTag: number }`.
  `returnEnum` is the enclosing function's return instantiation, and `returnFailTag` is the tag of `None` or `Err` in it.
- `ReadResult` and its builtin enum go away. `read_file`'s signature returns the `Result[string, string]`
  instantiation, which is marked used when `read_file` is called.

### 4.4 IR and lowering

IR types and instructions don't change. Lowering `try`:
1. Evaluate the operand into a local and read its tag.
2. Branch: if the tag is `okTag`, continue in a block that reads payload slot 0 as the expression's value.
3. Otherwise build the failure value in the return enum and return it. That is `enum_new` of `returnEnum` with
   `returnFailTag` and no payload for `Option`, or with the operand's `Err` payload (slot 0) for `Result`. A new value is
   always built, because `Result[T, E]` and `Result[U, E]` are different C types.

### 4.5 C backend

Enum names that contain `[` are generic instantiations, and they get their own mangling, so they can't collide with each
other or with non-generic names: `aster_G_` followed by the type string with `_` written as `__`, `[` as `_L`, `]` as
`_R`, and `, ` as `_C`. `Option[int]` becomes `aster_G_Option_Lint_R`, and `Result[[string], My_E]` becomes
`aster_G_Result_L_Lstring_R_CMy__E_R`. Non-generic enum mangling (`aster_E_<name>`) is unchanged.

### 4.6 Unchanged

The runtime, the driver and the CLI.

## 5. Self-hosted lexer and parser

**Lexer format.** `?` prints as `? S E ?`, the same as other punctuators.

**Tree format.** One row changes, and two are added:

| Node | Line | Children |
|------|------|----------|
| named type | `type S E name` | its type arguments, if any (the span now ends at `]`) |
| type parameter | `type-param NS NE name` | — (printed under `enum`, before the `variant` lines) |
| try | `try S E` | the operand |

**Parity first.** Both lexers learn `?`. `parse.aster` learns type parameters, type arguments and `?`, and the TS
conformance printer in `tests/parse_aster.test.ts` learns the same rows.

**Then the rewrites**, each keeping the suites green:
- Every `parse_*` function that can fail returns `Option[X]`. `expect` returns `Option[Token]`, and `fail` records the
  error and the caller returns `Option::None`. Every `let x: T = parse_t(p); if p.failed { return bad_*(); }` becomes
  `let x: T = parse_t(p)?;`.
- The two recovery points, the statement loop in `parse_block` and the item loop in `parse_program`, `match` on the
  `Option` and resynchronise on `None`. They replace the `p.failed = false` reset.
- `Parser.failed`, the six `bad_*()` functions, `ExprNode::Bad` (if it becomes unused), `MaybeType` and `MaybeExpr`
  are deleted. `Else` keeps its three variants, since it is not an option.
- `main` in both files matches `read_file`'s `Result`.

The copy of the lexer in `parse.aster` changes in step with `lex.aster`.

## 6. Testing

### 6.1 Golden programs

A new `generics/` folder:
- user generic enums: one and two parameters, a recursive `List[T]` and `Tree[T]`, a generic enum in a struct field
  and in an array, nested instantiations (`Option[Option[int]]`, `Result[[string], Point]`), and two instantiations of
  one enum in the same program
- inference from context in every listed context, and from payload values, including a slot fixed by an earlier
  value
- matching on instantiations with binders, `_` and or-patterns
- a program using two enums whose C names would collide without the `aster_G_` scheme (for example `enum A_L` and
  `A[…]`)

A new `try/` folder:
- `?` on `Option` and `Result` in `let` initialisers, arguments, binary operands, `return` values and expression
  statements
- a `?` chain (`f()?.field`), repeated `?` (`x??` on `Option[Option[int]]`), and `?` inside loops and `match` arms
- the failure path returns early and skips later side effects (each side effect prints, and the expected output proves
  the order)
- `Result` with an error type other than `string`
- `read_file(path)?` in a function returning `Result[string, string]`

`io/` programs that used `ReadResult` move to `Result`.

Additions to `errors/`:
- parse: `enum E[] {}`, `Option[]`, a trailing comma in each list, and `?` at the start of an expression
- declarations: a duplicate type parameter, a parameter that conflicts with `int`, a struct and `Option`, an unused
  parameter, two expansion cases (direct, and mutual through another enum), errors in an unused generic enum, and
  redefining `Option` and `Result`
- types: each arity error, `'Point' is not generic`, `'int' is not generic`, `'T' is not generic`, `T` outside its
  enum, and a `void` type argument
- inference: `Option::None` and `Result::Ok(1)` without context, and a slot conflict
- `?`: on an `int`, in a `void` function, in `main`, `Option`-in-`Result` and `Result`-in-`Option`, and an error type
  mismatch
- equality and `print` on an instantiation
- the existing `ReadResult` error programs are rewritten for `Result` or removed if they no longer test anything

### 6.2 Self-hosted fixtures

`fixtures/parse_generics.txt` (every type-parameter, type-argument and `?` form, and their parse errors) and
`fixtures/lex_question.txt` (a `?` in different positions). The existing fixture glob picks them up.

### 6.3 Unit tests

They follow the existing per-module pattern: the `?` token, the AST for the new forms, the checker's instantiation
table, inference and diagnostics, the IR for `try`, and the C mangling of instantiation names.

### 6.4 Workflow

As in v0.4: TDD per feature, golden tests first, then unit tests where a golden test can't reach. Implementation order:
lexer, parser, checker (types, then inference, then `?`), lowering and C, the `read_file` change, then the self-hosted
work in two steps (parity, then rewrites), then the docs. Each step commits with its tests.

## 7. Looking ahead (informing, not in scope)

- **Modules (v0.6).** With `parse.aster` slimmer, the copied lexer is the main remaining cost.
- **Generic functions** would allow `unwrap_or`, `map` and friends. The template and instantiation machinery here
  extends to function bodies.
- **Shared fields across enum variants** (friction entry 7) remain open.
