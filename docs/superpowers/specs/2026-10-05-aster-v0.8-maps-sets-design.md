# Aster v0.8: Maps and Sets (Design)

**Date:** 2026-10-05
**Status:** Approved in brainstorming
**Baseline:** `527cd36` (R2b merged; the compiler is self-hosted only).
**Friction source:** [`docs/self-host/friction.md`](../../self-host/friction.md), entry 11 (top of the v0.7 shortlist).

## 1. Purpose

The self-hosted checker fakes maps and sets with arrays:

- thirteen hand-written `find_*` lookups (the friction log counted twelve), two of which search backwards so that the latest entry wins;
- thirteen `contains` calls standing in for sets;
- scopes as `[[Local]]`;
- the generic-expansion SCC kept in parallel arrays.

Speed is not the problem. The cost is boilerplate, plus a search direction that is easy to get wrong. v0.8 adds built-in maps and sets, written once, in Aster only. It is the first feature landed under the release pipeline's **two-step rule**.

Decisions taken in brainstorming:

1. **Keys are `int` or `string` only.** That covers every use in the compiler. Widening it later is additive.
2. **The surface uses `Map[K, V]`/`Set[K]` types, a context-typed `{}` for an empty value, and `map_*`/`set_*` builtins.** That's consistent with `Option[T]`, `[]` and `push`/`len`. There are no methods and no index syntax.
3. **Iteration is in insertion order, and the language guarantees it.** The compiler's output must be deterministic for the self-hosting fixed point.
4. **The implementation is an insertion-ordered hash table in the C runtime**, reached through new IR instructions. Both backends call it.
5. **It ships as two PRs.** v0.8a adds the feature, and v0.8b, after v0.8a's release, rewrites the compiler onto it.

### Non-goals

Map literals with entries (`{"a": 1}`). Key types other than `int` and `string`. Equality or printing of maps and sets. `for (k, v) in m` iteration syntax (the v0.9 candidate). Generic functions. Freeing memory.

## 2. Language surface

### Types

| Type | Meaning |
|---|---|
| `Map[K, V]` | A reference to a mutable map from `K` to `V`. `K` is `int` or `string`. `V` is any type except `void`. |
| `Set[K]` | A reference to a mutable set of `K`. `K` is `int` or `string`. |

- Like arrays and structs, maps and sets are heap-allocated **references**: assignment, argument passing and returning share one object.
- `Map[K1, V1]` equals `Map[K2, V2]` when `K1 = K2` and `V1 = V2`. `Set[K1]` equals `Set[K2]` when `K1 = K2`.
- `Map` and `Set` are built-in type names, so declaring a struct or enum with either name is `'Map' is a builtin type and cannot be redefined` (the existing `Option`/`Result` message).

**Type errors**, in the order they are checked:

- A key type other than `int` or `string`: `map key must be int or string, found <T>` for both `Map` and `Set`.
- `V` of `void`: `map value cannot be void`.
- The wrong number of type arguments: `'Map' expects 2 type argument(s), got <n>` and `'Set' expects 1 type argument(s), got <n>`. These use the existing generic-arity message.

### The empty literal `{}`

- In expression position, `{` immediately followed by `}` is the empty map/set literal. It takes its type from context, through the same contexts that type an empty `[]`:
  - a `let`/`var` type,
  - an assignment target,
  - a function argument,
  - a `return` value,
  - a struct literal field,
  - a variant payload value,
  - `push`'s second argument,
  - an array literal element,
  - an `if`-expression or `match`-expression arm in one of those positions.
- The context type must be a `Map` or a `Set`. Otherwise it's a type mismatch: `type mismatch: expected <T>, found empty map or set`.
- With no context, it's `cannot infer type of empty map or set`.
- At the start of a statement, `{` still opens a block. `{}` as a statement is an empty block, as today.
- There are no literals with entries.

### Builtins

| Builtin | Signature | Behaviour |
|---|---|---|
| `map_set` | `(m: Map[K, V], k: K, v: V): void` | Inserts or overwrites. Overwriting keeps the key's original position. |
| `map_get` | `(m: Map[K, V], k: K): Option[V]` | `Option::Some(v)` or `Option::None`. |
| `map_has` | `(m: Map[K, V], k: K): bool` | |
| `map_remove` | `(m: Map[K, V], k: K): bool` | `true` if the key was present. |
| `map_keys` | `(m: Map[K, V]): [K]` | A fresh array of the keys, in insertion order. |
| `set_add` | `(s: Set[K], k: K): bool` | `true` if `k` was not already present. |
| `set_has` | `(s: Set[K], k: K): bool` | |
| `set_remove` | `(s: Set[K], k: K): bool` | `true` if `k` was present. |
| `set_items` | `(s: Set[K]): [K]` | A fresh array of the elements, in insertion order. |
| `len` | also `(m: Map[K, V]): int` and `(s: Set[K]): int` | The number of entries. |

**Argument errors** reuse the existing builtin messages:

- `function '<name>' expects <n> argument(s), found <m>`.
- `function '<name>' expects a map, found <T>` and `function '<name>' expects a set, found <T>` for the first argument.
- `type mismatch: expected <K>, found <T>` for keys and values.
- `len`'s message becomes `function 'len' expects a string, array, map or set, found <T>`.

All the builtin names are reserved, like the existing builtins: a user function with one of these names is `'<name>' is a builtin function and cannot be redefined`.

### Order

Iteration (`map_keys`, `set_items`) follows insertion order:

- Overwriting with `map_set` doesn't move a key.
- Removing a key and adding it again puts it at the end.

This order is part of the language definition.

### Equality, printing, panics

- `==`/`!=` on maps or sets is `cannot compare '<T>' values`, like arrays.
- `print` is `cannot print a value of type <T>`.
- There are no new runtime panics: a missing key is `None` or `false`, and memory exhaustion is the existing `out of memory`.

## 3. Implementation

### Runtime (`runtime/aster_rt.{c,h}`)

The runtime gets an insertion-ordered hash table, the same layout as CPython's dict:

- `entries`: a dense array of `{ uint64 hash; int64 ikey; aster_string skey; unsigned char value[value_size] }` records, plus a `tombstone` flag per entry.
- `index`: an open-addressing table of `int32` entry indices, with `-1` meaning empty. Its capacity is a power of two, it uses linear probing, and it grows at 2/3 load. When tombstones exceed half the entries, the next growth compacts `entries`, keeping order.
- Hashing: FNV-1a 64-bit for strings, and a 64-bit mix (splitmix64 finaliser) for ints.
- The key kind (`ASTER_KEY_INT = 0` or `ASTER_KEY_STRING = 1`) and `value_size` are fixed at creation. A set is a map with `value_size == 0`.

The runtime API:

```c
typedef struct aster_map_obj *aster_map;
aster_map aster_rt_map_new(int64_t key_kind, int64_t value_size);
void     *aster_rt_map_slot(aster_map m, int64_t ikey, aster_string skey, int64_t create); /* value ptr, or NULL if absent and !create */
int64_t   aster_rt_map_insert(aster_map m, int64_t ikey, aster_string skey);              /* 1 if newly inserted */
int64_t   aster_rt_map_remove(aster_map m, int64_t ikey, aster_string skey);              /* 1 if removed */
int64_t   aster_rt_map_len(aster_map m);
aster_array aster_rt_map_keys(aster_map m);                                               /* fresh array, insertion order */
```

- The key goes in whichever of `ikey`/`skey` matches the kind; the other argument is ignored.
- `slot` with `create` returns a pointer to zeroed value bytes for a new key.
- `runtime.aster` is regenerated with `pnpm gen:runtime`.

### Front end

- **Lexer:** no change.
- **Parser:** the primary-expression parser recognises `{` `}` as `Expr::EmptyMap`. Statement-level `{` is untouched.
- **Checker:**
  - `Type` gains `Map(Type, Type)` and `Set(Type)`.
  - Type resolution handles `Map[...]`/`Set[...]` with the errors in §2.
  - `Map` and `Set` join the reserved built-in type names.
  - The builtin call checker gets the nine new builtins and `len`'s extension.
  - `{}` is typed at every `[]` context site.
  - `map_get` instantiates `Option[V]` the way `?` and variant construction do.
  - The type printer prints `Map[K, V]` and `Set[K]`, with `, ` between arguments.
- **typed_dump.aster** prints the new types and the `EmptyMap` node.

### IR and lowering

New `IrInstr` variants:

```
MapNew(dst, key: Type, value: Type)        // value is Void for sets
MapValue(dst, map, key)                    // dst: V; the key is known to be present
MapSet(map, key, value)
MapInsert(dst, map, key)                   // set_add: dst bool
MapHas(dst, map, key)
MapRemove(dst, map, key)
MapLen(dst, map)
MapKeys(dst, map)                          // dst: [K]
```

- Lowering maps each builtin onto one instruction: `set_has` → `MapHas`, `set_remove` → `MapRemove` and `set_items` → `MapKeys`.
- `map_get` is lowered the way `read_file` builds its `Result`: `MapHas`, then a branch. The present branch does `MapValue`, then `EnumNew(Some)`, and the absent branch does `EnumNew(None)`, both joining afterwards. The emitters never build enums. The checker registers the `Option[V]` instantiation, so the enum is emitted.
- `ir_print.aster` prints each instruction in the existing style.

### Backends

- **`emit.aster` (C):**
  - `Map`/`Set` types map to `aster_map`.
  - Each instruction becomes a runtime call. Key arguments are `(ikey, skey)`, with a zero value for the unused one.
  - `MapValue` reads `*(V *)aster_rt_map_slot(..., 0)`.
  - `MapSet` calls `slot(..., 1)` and stores `*(V*)slot = v`.
- **`emit_llvm.aster`:** the same calls, declared in the declare list. Value reads and writes go through the slot pointer with `llvm_size(V)`, as `IndexGet`/`IndexSet` do for arrays. `tests/llvm_backend.test.ts` checks every declare against `aster_rt.h`, so the two must agree.

## 4. Rollout

### v0.8a: the feature (one PR)

Everything in §2–§3. **`packages/asterc-self` must not use maps or sets in its own source.** The base release must be able to build it, and `release-bootstrap` enforces that. It may of course implement them.

### v0.8b: dogfooding (a separate PR, merged after v0.8a's release is published)

Rewrite the compiler onto maps and sets:

- `checker.aster`'s `find_*` searches;
- the `contains`-based sets;
- scopes `[[Local]]` → `[Map[string, Local]]`, where the latest entry winning comes from `map_set` overwriting;
- the SCC `ExpansionGraph` arrays;
- `loader.aster`'s seen-files set.

**Every committed golden must stay byte-identical.** Diagnostics, their order and the typed summaries must not change. That is the proof that the refactor preserved behaviour. Emitted C may change, because the fixed point is checked against the PR's own source. Self-check timings before and after are recorded in the PR (informational only).

## 5. Testing

v0.8a:

- **Corpus programs** in `tests/programs/maps/`, with inline `// expect-stdout`/`// expect-exit` headers. They run through `selfhost_golden` (C backend) and `llvm_backend` (LLVM):
  - basics (set, get, overwrite, has, remove, len);
  - insertion order through overwrite, remove and re-add;
  - int and string keys, including the empty string, negative ints and colliding hashes;
  - struct, array, enum and nested-map values, with reference sharing;
  - sets;
  - maps passed to and returned from functions and stored in struct fields;
  - a 100 000-entry growth and removal stress test;
  - `{}` in every context from §2.
- **Error programs** in `tests/programs/errors/maps_*.aster`, one per diagnostic in §2. They are checked by the `expect-error` assertion and pinned by the CLI goldens.
- **Goldens:** `pnpm golden` adds the new corpus files' check and CLI goldens, and the diff is reviewed. No existing golden may change.
- **Runtime unit test:** `tests/runtime_map.test.ts` compiles a C harness against `runtime/aster_rt.c`. It checks forced hash collisions, tombstone reuse, compaction keeping order, growth past several resizes, and zeroed new slots.
- **Spec conformance:** `docs/spec/language.md` gets the types table, the `{}` rule, the Builtins table, the order rule, and "Not in v0.7" renamed to "Not in v0.8".
- **Warnings:** the runtime stays clean under `-Wall -Wextra -Werror`.
- **CI:** all the `proof` legs (S1, S2, S3, SL1, full) and `release-bootstrap` pass.

v0.8b: the full suite with no golden changes, the `proof` legs, and the line-count reduction recorded in friction.md (entry 11 marked resolved).
