# Aster v0.6: Imports (Design)

**Date:** 2026-10-03
**Status:** Approved in brainstorming
**Builds on:** [`2026-10-03-aster-v0.5-design.md`](2026-10-03-aster-v0.5-design.md). Everything in v0–v0.5 still holds unless this document changes it.

## 1. Purpose

Friction-log entry 2 ([`docs/self-host/friction.md`](../../self-host/friction.md), shortlist item 2) is the last costly one:
`parse.aster` starts with a 184-line copy of `lex.aster`'s lexer, and a checker written in Aster would have to copy both.
v0.6 lets a program span several files, with one flat namespace.

### Success criteria

v0.6 is done when:

1. The golden suite covers every feature in §3, including every new compile error, with multi-file programs.
2. `lex.aster` is split into a library, `lexer.aster`, and a thin `lex.aster` driver. `parse.aster` deletes its copy of the
   lexer and imports `lexer.aster`. Both conformance suites pass over the whole corpus, which now includes `import` items.
3. `docs/spec/language.md`, `README.md` and `docs/self-host/friction.md` describe v0.6. The friction log marks entry 2 as
   resolved, with before and after line counts for `parse.aster`.

### Non-goals for v0.6

Qualified names (`lexer::Token`), visibility (`pub`), selective imports, search paths or packages, separate
compilation, and `defer`.

## 2. Semantics decisions (summary)

- **`import "path";` is a top-level item.** It names a file relative to the importing file's directory.
- **One flat namespace.** Every top-level item of every loaded file joins the program. A name declared twice is an error,
  whichever files the declarations are in.
- **Each file is loaded once**, keyed by its real path, so diamond and cyclic imports are fine.
- **`main` belongs to the root file**, the one passed to the compiler. An imported file may not declare it.
- **Spans become global offsets.** Each file gets a base offset in one source map. The AST, checker and IR keep plain
  `{ start, end }` spans. Diagnostics map an offset back to a file, line and column.

## 3. Language changes

### 3.1 Lexical

`import` is a new keyword.

### 3.2 Grammar

```
item        = function | structDecl | enumDecl | importDecl ;
importDecl  = "import" STRING ";" ;
```

Imports may appear anywhere among the items of a file.

### 3.3 Loading

- The **root file** is the file given to the compiler. Loading starts there.
- An import's path is the string literal's value. A relative path resolves against the directory of the file that
  contains the import. An absolute path is used as is. Any file name is allowed. `.aster` is a convention, not a rule.
- Files are identified by their real path, with symlinks resolved. A file already loaded is not loaded again, so a file
  that imports itself, two files that import each other, and two imports of a shared file are all fine.
- **Load order** is the root first, then each import depth first, in the order the imports appear: a pre-order walk that
  skips files already loaded.
- A file that can't be read is the error `cannot import '<path>': <reason>`, at the import's string literal. `<path>` is
  the literal's value as written, and `<reason>` is the OS's reason, as for `read_file` (`No such file or directory`, `Is a
  directory`, …). A path containing `\0` gives the reason `invalid path`.
- Every loaded file is lexed and parsed. If any file has lexical or syntax errors, compilation stops after loading, with
  every file's syntax errors reported, and nothing is checked. That is the same rule as for a single file.

### 3.4 Program assembly

- The items of every loaded file form one program, in load order. The checker sees them as if they had been written in
  one file in that order.
- Names keep their existing rules, applied across files. A collision is reported with the existing messages
  (`duplicate function 'f'`, `duplicate struct 'S'`, `'X' is already declared as a struct`, and so on), at the declaration
  that comes later in load order.
- `main` must be declared in the root file. A function named `main` in any other file is the error
  `'main' must be declared in the root file`, at its name, and that declaration is otherwise ignored. A missing `main` in
  the root is reported as now, even when another file declared one.
- Import items have no other meaning. An unused import is not an error.

### 3.5 Diagnostics

- A diagnostic belongs to the file that contains its span. The CLI prints the path of that file as the compiler reached
  it: the root path as given on the command line, and an imported path joined to its importer's path
  (`programs/lexer.aster:12:5: error: …`).
- The short form used by golden tests is `L:C message` for the root file, and `path:L:C message` for any other file,
  where `path` is relative to the root file's directory, with `/` as the separator.
- Diagnostics are still sorted by position. Global offsets sort by load order, then by position within a file.
- `cannot import` diagnostics are reported together with syntax errors.

### 3.6 CLI

`check`, `build` and `run` load the whole program. `--emit=tokens` and `--emit=ast` show the root file only, and
don't follow imports (the root's imports appear in the AST as items). `--emit=ir` and `--emit=c` show the whole program.

## 4. Compiler changes

### 4.1 Source map

- `SourceFile` keeps `path`, `text` and `lineStarts`, and gains `base: number`, the global offset of its first
  character. `makeSource(path, text)` keeps its signature and gives `base: 0`.
- A new `SourceMap` holds the loaded files in load order. Each file's base is the previous file's base plus its text
  length plus 1, so no offset belongs to two files and an end-of-file offset stays inside its own file.
  `sourceAt(map, offset)` returns the file containing an offset.
- `lineCol`, `formatDiagnostic` and `formatShort` take a `SourceMap` (or a single `SourceFile`, which acts as a one-file
  map) and subtract the base before computing lines.

### 4.2 Lexer and parser

- `lex(source)` adds `source.base` to every span it produces.
- Tokens gain the `import` keyword. The parser gains `ImportDecl = { kind: 'import'; path: string; pathSpan: Span; span: Span }`,
  and `Program` gains `imports: ImportDecl[]`.

### 4.3 Loader

A new `driver/load.ts`:
`loadProgram(root: SourceFile, host: LoadHost): { map: SourceMap; program: Program; rootEnd: number; diagnostics: Diagnostic[] }`.
- `LoadHost` has `readFile(path): { ok: true; text: string } | { ok: false; reason: string }` and `realPath(path): string`.
  The Node host uses `fs`, and tests can pass an in-memory host.
- It merges each file's `functions`, `structs` and `enums` into one `Program` in load order, and reports `cannot import`
  and every file's lexical and syntax errors.
- The checker is unchanged except for the `main` rule (§3.4). It needs to know which declarations are in the root, which
  it can tell from their spans: a declaration is in the root when its span start is below the root's end offset.

### 4.4 Pipeline and public API

- `runFrontend(root: SourceFile, host?)` and `compileToC(root: SourceFile, host?)` keep their first parameter. The root's
  text is taken from the `SourceFile`, and its imports resolve against `dirname(root.path)` through the host (Node `fs` by
  default), so existing call sites keep working. Both return the `SourceMap` with their results, so callers can format
  diagnostics from any file.
- `index.ts` exports `loadProgram`, `SourceMap` and the host type.

### 4.5 Unchanged

The checker's type rules, the IR, lowering, the C backend and the runtime.

## 5. Self-hosted lexer and parser

- **Split.** `tests/programs/programs/lexer.aster` holds `Token`, `LexError`, `Lexer`, the byte predicates, `lex` and
  their helpers, with the byte reader named `peek_byte` (the name `parse.aster`'s copy already uses, because the parser
  has its own `peek`). It has no `main`, and its header starts with `// expect-library`.
- `lex.aster` keeps its header, `report` and `main`, and imports `lexer.aster`.
- `parse.aster` deletes its `// ---- lexer` section and imports `lexer.aster`.
- **Parity.** Both lexers treat `import` as a keyword. `parse.aster` parses `importDecl` and prints it as
  `import S E "path"` (the string literal's source text), in source order with the other items. The TS reference printer
  in `tests/parse_aster.test.ts` prints the same.
- Each conformance test compiles its program from its real path, so the import resolves.

## 6. Testing

### 6.1 Harness

- A new directive, `// expect-library`, marks a file that is only ever imported. The golden suite doesn't compile it as
  a root, but both conformance suites still lex and parse it, as they do every `.aster` file.
- Golden programs are compiled from their real paths, so their imports resolve. Error expectations for other files use
  the `path:L:C message` form.

### 6.2 Golden programs

A new `modules/` folder:
- a root that imports a library of functions, structs and enums, and uses all three
- a diamond (the root imports `a` and `b`, which both import `shared`) and a cycle (`a` imports `b`, which imports `a`),
  each loaded once
- a file that imports itself
- an import from a subdirectory, whose own relative import resolves against that subdirectory
- items used before their import in source order, and a type declared in one file and used in another
- generic enums and `?` across files

Additions to `errors/` (with library files next to them):
- `cannot import` for a missing file and for a directory
- a duplicate function, struct and enum across two files, and a struct/enum collision across files, each reported at the
  later declaration in load order (in the imported file, with the `path:L:C` form)
- `main` in an imported file
- a syntax error in an imported file, which stops compilation and is reported with its path
- a type error in an imported file, reported with its path

### 6.3 Self-hosted fixtures

`fixtures/parse_imports.txt`: imports among other items, and the parse errors `import;`, `import "a"` with no `;`, and
`import x;`.

### 6.4 Unit tests

They follow the existing per-module pattern: the `import` token, the AST for `ImportDecl`, the source map
(`sourceAt`, base layout, `lineCol` across files), the loader with an in-memory host (load order, dedup by real path,
cycles, every error), and `formatShort` across files.

### 6.5 Workflow

As in v0.5: TDD per feature, golden tests first where they reach. Implementation order: lexer and parser, then
self-hosted parity for the `import` syntax, then the source map and spans, the loader and pipeline, the harness and
goldens, then the self-hosted split, then the docs. Each step commits with its tests.

## 7. Looking ahead (informing, not in scope)

- With imports in, a checker written in Aster (`check.aster`) is the obvious next dogfood target.
- Name collisions in the flat namespace (`peek` vs `peek_byte`) are the first cost of not having qualified names. The
  friction log should track how often they bite.
- `defer` (from v0.5's friction findings) remains open.
