# Aster v0.3: Input and Program Arguments (Design)

**Date:** 2026-10-02
**Status:** Approved in brainstorming, pending spec review
**Builds on:** [`2026-10-02-aster-v0.2-design.md`](2026-10-02-aster-v0.2-design.md). Everything in v0, v0.1 and v0.2 still holds unless this document changes it.

## 1. Purpose

v0.3 is the last of three milestones toward a self-hosted Aster compiler:

| Milestone | Adds |
|-----------|------|
| v0.1 | Structs, growable arrays, compound assignment, `for` loops |
| v0.2 | Enums with positional payloads and an exhaustive `match` |
| **v0.3** (this spec) | File/stdin input and program arguments |

Until now every Aster program has worked on hard-coded data. A compiler has to read a source file named on its command line. v0.3 adds just enough for that: read a whole file, read all of stdin, and receive the command-line arguments.

There are no generics and no null, so `read_file` reports failure through a predeclared enum, `ReadResult`. Callers must `match` on it, and v0.2's exhaustiveness check makes them handle the error case.

### Success criteria

v0.3 is done when:

1. The golden suite covers every feature in §3, including every new compile error.
2. A new "real program" passes: `programs/lex.aster` is the Aster lexer written in Aster. It reads the file named by its single argument and prints its tokens and lexical errors in the format in §5.2.
   - Its golden test lexes a small fixture.
   - A separate test, `tests/lex_aster.test.ts`, runs it on every `.aster` file in `tests/programs/` (itself included) and on the lexer fixtures, and checks that its output matches the TypeScript lexer's, rendered in the same format.
3. `docs/spec/language.md` and `README.md` describe v0.3.

### Non-goals for v0.3

Writing files, writing to stderr or stdout without a newline, line-at-a-time stdin, environment variables, exit without returning from `main`, directory listing, a generic `Result` type, generics, a standard library written in Aster, and an LLVM backend.

## 2. Semantics decisions (summary)

- **`ReadResult` is a predeclared enum.** Every program behaves as if it began with `enum ReadResult { Ok(string), Err(string) }`. It is an ordinary enum in every other respect.
- **`read_file` never panics.** Every failure becomes `ReadResult::Err` with a message naming the path and the OS reason.
- **`read_stdin` reads to EOF and panics on a read error.** A read error on stdin is rare and nothing useful can be done about it.
- **`main` may take the arguments.** `fn main(args: [string]): int` is legal alongside `fn main(): int`. The array holds the arguments without the program name.
- **`aster run` passes everything after `--` to the program.**

## 3. Language changes

### 3.1 Lexical

No changes. `ReadResult`, `read_file` and `read_stdin` are ordinary identifiers that the checker treats specially.

### 3.2 Types

`ReadResult` joins the type namespace as a predeclared enum:

```
enum ReadResult { Ok(string), Err(string) }
```

- `Ok` has tag 0 and `Err` tag 1.
- It carries payloads, so its values are heap-allocated references. `==`/`!=` and `print` reject it as they reject any other payload enum.
- Programs may use it anywhere a type is allowed and may build values themselves: `ReadResult::Err("bad input")`.

### 3.3 Grammar

No changes.

### 3.4 Declarations and name resolution

- `ReadResult` cannot be redeclared. A struct, enum or function named `ReadResult` is the error `'ReadResult' is a builtin type and cannot be redefined`, reported at the declaration's name.
- `read_file` and `read_stdin` are builtins, so the existing rule applies: a function or type with either name is `'<name>' is a builtin function and cannot be redefined`.
- **`main`.** Exactly one of these signatures is accepted. The parameter may have any name.
  - `fn main(): int`
  - `fn main(<name>: [string]): int`

  Anything else is `'main' must have signature 'fn main(): int' or 'fn main(args: [string]): int'`, reported where the current message is. The `missing 'fn main(): int'` error is unchanged.

### 3.5 Builtins

| Builtin | Signature | Behaviour |
|---------|-----------|-----------|
| `read_file` | `(path: string): ReadResult` | Reads the whole file. On success, `Ok(contents)`; on failure, `Err(message)`. |
| `read_stdin` | `(): string` | Reads stdin to EOF. |

**`read_file`**
- The contents are the file's raw bytes, with no newline translation or encoding check. An empty file gives `Ok("")`.
- A relative path resolves against the process's working directory.
- Failure messages are `<path>: <reason>`, where `<path>` is the argument as given and `<reason>` is the C library's `strerror` text for the failure:
  - a missing file: `nope.txt: No such file or directory`
  - a directory: `src: Is a directory`
  - no permission: `secret.txt: Permission denied`
- A path containing a `\0` byte cannot be passed to the OS. It gives `Err("<path>: invalid path")` without touching the filesystem. In the message, the path is printed up to its first `\0`.

**`read_stdin`**
- Returns every remaining byte of stdin. Once stdin is at EOF, later calls return `""`.
- A read error panics with `cannot read stdin: <reason>`.

**`main(args)`**
- `args` holds `argv[1..]` as strings, in order. The program name is not included. With no arguments, `args` is empty.
- It is a fresh, ordinary array: `push` and `pop` work on it.

### 3.6 Runtime

One new panic: `cannot read stdin: <reason>`.

### 3.7 CLI

- `aster run <file.aster> [-- <args>…]`. Everything after `--` is passed to the program unchanged, including arguments that start with `-`. Without `--`, extra arguments remain the usage error `unexpected argument`.
- `aster build` and `aster check` do not accept `--`.
- Built executables take their arguments directly: `./prog a b`.
- Stdin already passes through `aster run`.

### 3.8 Example

```
fn count_lines(s: string): int {
    var n: int = 0;
    for i in 0..len(s) {
        if byte_at(s, i) == 10 {
            n += 1;
        }
    }
    return n;
}

fn main(args: [string]): int {
    if len(args) != 1 {
        print("usage: lines <file>");
        return 2;
    }
    match read_file(args[0]) {
        ReadResult::Ok(text) => print(count_lines(text)),
        ReadResult::Err(msg) => {
            print(msg);
            return 1;
        }
    }
    return 0;
}
```

```
$ aster run lines.aster -- notes.txt
42
$ aster run lines.aster -- nope.txt
nope.txt: No such file or directory
```

## 4. Compiler changes

### 4.1 Checker

- **The predeclared enum.** `check()` seeds `env.enums` with `ReadResult` before `collectTypes` runs, using the existing `TEnum` shape (`payloadFree: false`, variants `Ok` tag 0 and `Err` tag 1, each with payload `[string]`). User declarations named `ReadResult` are rejected in `collectTypes` and in function collection (§3.4).
- **Emitted only when used.** `TypedProgram.enums` includes `ReadResult` only if the program mentions it: in a type, a variant expression, a pattern, or a `read_file` call. The checker sets a flag at each of those points, and when the flag is set it puts `ReadResult` first in `enums`. Programs that never mention it produce exactly the IR and C they do today.
- **Builtins.** `read_file` and `read_stdin` join `BuiltinName` and `BUILTIN_SIGNATURES`. `read_stdin` is the first zero-parameter signature builtin; the existing arity check covers it.
- **`main`.** The signature check at the current location accepts both forms in §3.4.

### 4.2 IR and lowering

**`read_stdin`** lowers to `call_builtin read_stdin`. `IrBuiltin` gains `read_stdin`.

**`read_file`** gets a dedicated instruction, because the IR has no address-of and the runtime cannot build enum values (enum layouts are emitted per program):

| Instruction | Meaning |
|-------------|---------|
| `read_file ok, text, path` | Reads the file at `path`. Sets the `bool` local `ok`, and sets the `string` local `text` to the contents when `ok` is true and to the error message otherwise. |

`read_file(p)` lowers to:

```
read_file t_ok, t_text, p
br t_ok, L_ok, L_err
L_ok:   dst = enum_new ReadResult::Ok(t_text);  jmp L_join
L_err:  dst = enum_new ReadResult::Err(t_text); jmp L_join
L_join:
```

The backends never see `ReadResult` as anything but an ordinary enum. The IR printer prints the new instruction.

### 4.3 C backend

- `read_file` emits `text = aster_rt_read_file(path, &ok);`. IR locals are C locals, so taking their address is fine.
- **The `main` wrapper.** For `fn main(): int` it stays `int main(void) { return (int)aster_fn_main(); }`. For `main(args)` it becomes:
  ```c
  int main(int argc, char **argv) { return (int)aster_fn_main(aster_rt_args(argc, argv)); }
  ```
- `ReadResult` is mangled and laid out like any payload enum: `aster_E_ReadResult` with members `v_Ok` and `v_Err`.

### 4.4 Runtime

New functions in `aster_rt.h` / `aster_rt.c`:

| Function | Behaviour |
|----------|-----------|
| `aster_string aster_rt_read_file(aster_string path, bool *ok)` | §3.5. Builds a NUL-terminated copy of the path for `fopen`, reads with `fread` into a buffer that doubles as it grows (so it works for files whose size `fseek` cannot report), and turns `ferror` (which is how reading a directory fails on Linux) into an `Err` message from `errno`. |
| `aster_string aster_rt_read_stdin(void)` | Reads stdin to EOF the same way. Panics on `ferror`. |
| `aster_array aster_rt_args(int argc, char **argv)` | Builds a `[string]` of `argv[1..argc)`. The strings point at `argv` directly, with lengths from `strlen`. |

Buffers come from the runtime's existing allocator and are never freed.

### 4.5 CLI

`parseArgs` learns `--` for `run`: everything after it becomes `programArgs`, and `runProgram` passes them to the executable. The usage text gains `[-- <args>…]` on the `run` line.

### 4.6 Unchanged

- The lexer, the parser and the AST.
- The `Type` union, since `ReadResult` is `{ kind: 'enum', name: 'ReadResult' }`.
- Diagnostic formatting, the cc invocation and exit codes.

## 5. Testing

### 5.1 Golden harness

`tests/harness.ts` gains two directives:

- `// expect-args: a b c` gives the program's arguments, split on whitespace. Arguments containing spaces cannot be written. They are not needed yet.
- `// expect-stdin:` followed by continuation comment lines gives stdin. Lines are joined the way `expect-stdout` joins them.

`tests/golden.test.ts` changes:
- It passes the arguments and the stdin text to `spawnSync`. A program without `expect-stdin` gets empty stdin rather than inheriting the test runner's, so every golden run is deterministic.
- It runs each program with its working directory set to the folder containing the `.aster` file, so tests can read fixtures by relative path.
- It skips any `fixtures/` folder when discovering programs.

### 5.2 The lexer output format

`lex.aster` and the comparison test both use this line format:

- One line per token, in order, ending with `eof`: `<kind> <start> <end> <text>`. The kind is the TypeScript `TokenKind` string. `start` and `end` are byte offsets. For `eof`, the line is `eof <n> <n>`, with no trailing space.
- Then one line per lexical error, in the order the lexer reports them: `error <start> <end> <message>`, with the messages from `lexer.ts`.
- Exit code 0 when there are no errors and 1 when there are. `lex.aster` exits 2 with a usage message for the wrong number of arguments, and prints the `Err` message and exits 2 when the file can't be read.

The comparison test converts the TypeScript lexer's UTF-16 offsets to UTF-8 byte offsets. Corpus files must be valid UTF-8. A token's text never contains a newline, so one line per token is unambiguous.

### 5.3 Golden programs

A new `io/` folder:
- `read_file` on a fixture: contents printed, `len` in bytes for a file with non-ASCII text, an empty file
- `Err` for a missing file, a directory, and a path containing `\0`
- `read_stdin` with `expect-stdin`, with empty stdin, and called twice
- `main(args)` with several arguments, with none, and `push` onto `args`
- `ReadResult` values built by hand, passed to and returned from functions, and stored in a struct

Additions to `errors/`:
- a struct, an enum and a function named `ReadResult`
- a function named `read_file`
- `read_file` with the wrong arity and the wrong argument type, `read_stdin` with an argument
- `print` of a `ReadResult`, `==` on `ReadResult`
- a non-exhaustive match on `read_file(...)`
- `main` signatures: `main(args: [int])`, `main(args: string)`, `main(a: [string], b: int)`, `main(args: [string]): void`

Real program: `programs/lex.aster`, with fixtures in `programs/fixtures/` (a small valid sample, and one containing each lexical error and a non-ASCII unexpected character).

`tests/lex_aster.test.ts` builds `lex.aster` once and compares its output with the TypeScript lexer on every corpus file (§1).

### 5.4 Unit tests

- **Checker:** both `main` forms accepted; `ReadResult` present in `TypedProgram.enums` only when mentioned.
- **Lowering snapshot:** `read_file` lowered to the instruction, the branch and the two `enum_new`s.
- **Emitter:** the `read_file` instruction; both `main` wrappers.
- **CLI:** `run -- a -b` passes `["a", "-b"]`; `build` with `--` is a usage error.

### 5.5 Workflow

As before:
- TDD, with a failing golden program or unit test first.
- Conventional commits.
- CI runs typecheck, lint and test.

The harness changes (§5.1) land first and must change no existing test results.

## 6. Looking ahead (informing, not in scope)

- With v0.3, the self-hosting work can start: the lexer in this spec is its first piece. Writing it will show which missing features hurt most. Likely candidates are writing to stderr, a never type, nested patterns and generics.
- The `read_file` instruction maps onto LLVM as a call that takes the address of an `alloca`, so it needs no special treatment there.
