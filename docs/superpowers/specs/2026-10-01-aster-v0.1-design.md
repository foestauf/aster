# Aster v0.1: Structs, Arrays and Loops (Design)

**Date:** 2026-10-01
**Status:** Approved in brainstorming, pending spec review
**Builds on:** [`2026-10-01-aster-v0-design.md`](2026-10-01-aster-v0-design.md). Everything in v0 still holds unless this document changes it.

## 1. Purpose

v0.1 is the first of three milestones toward a self-hosted Aster compiler:

| Milestone | Adds |
|-----------|------|
| **v0.1** (this spec) | Structs, growable arrays, compound assignment, `for` loops |
| v0.2 | Enums with payloads and an exhaustive `match` |
| v0.3 | File/stdin input and program arguments |

Each milestone gets its own spec, plan and build cycle. v0.1 lays the groundwork for the other two: aggregate types, reference semantics, and a structured type representation inside the compiler.

### Success criteria

v0.1 is done when:

1. The type-representation refactor (§4.1) has landed as its own commit, and the existing golden suite and unit tests pass unchanged.
2. The golden suite covers every feature in §3, including every new compile error and runtime panic.
3. Two new "real program" golden tests pass:
   - `programs/tokenizer_structs.aster` is the v0 tokenizer rewritten with a `Token` struct and a `[Token]` array.
   - `programs/rpn.aster` is a stack-based RPN calculator over a token array. It uses `push`/`pop`, and a companion program in `panics/` covers popping an empty stack.
4. `docs/spec/language.md` and `README.md` describe v0.1.

### Non-goals for v0.1

Enums, `match`, null or optional values, generics, equality on structs or arrays, printing structs or arrays, methods, I/O beyond `print`, freeing memory, C-style `for`, `..` as a general expression, slices, and an LLVM backend.

## 2. Semantics decisions (summary)

- **Structs and arrays are heap-allocated references.** Assignment, argument passing and returning share the same object. Nothing is freed (as with v0 strings), and memory is reclaimed when the process exits.
- **No null.** Every struct literal must initialise every field, so every reference is always valid. A struct type that contains itself directly (`struct L { next: L }`) is legal but cannot be constructed until v0.2 adds enums.
- **`let`/`var` control the binding only.** The contents of a struct or array are always mutable. `let a: [int] = []; push(a, 1);` is legal; `a = [2];` is not.

## 3. Language changes

### 3.1 Lexical

- New keywords: `struct`, `for`, `in`.
- New punctuation: `.`, `..`, `[`, `]`, `+=`, `-=`, `*=`, `/=`, `%=`.
- The lexer uses maximal munch: `..` is one token, and `1..5` lexes as `1`, `..`, `5`.

### 3.2 Types

| Type | Meaning |
|------|---------|
| `Name` | A reference to an instance of the struct `Name`. |
| `[T]` | A reference to a growable array of `T`. `T` may be any type except `void`, including another array (`[[int]]`) or a struct. |

Type equality:
- Structural for arrays: `[T]` equals `[U]` exactly when `T` equals `U`.
- Nominal for structs: two structs are equal only if they have the same name.

There are still no implicit conversions.

### 3.3 Grammar

This shows only the rules that change or are new relative to v0 §3.3. Everything else is unchanged.

```
program     = { item } EOF ;
item        = function | structDecl ;
structDecl  = "struct" IDENT "{" [ fieldDecl { "," fieldDecl } [ "," ] ] "}" ;
fieldDecl   = IDENT ":" type ;

type        = IDENT | "[" type "]" ;

statement   = "let" IDENT ":" type "=" expr ";"
            | "var" IDENT ":" type "=" expr ";"
            | ifStmt
            | "while" expr block
            | forStmt
            | "break" ";"
            | "continue" ";"
            | "return" [ expr ] ";"
            | block
            | expr [ assignOp expr ] ";" ;
assignOp    = "=" | "+=" | "-=" | "*=" | "/=" | "%=" ;
forStmt     = "for" IDENT "in" expr [ ".." expr ] block ;

postfix     = primary { "(" [ expr { "," expr } ] ")"
                      | "." IDENT
                      | "[" expr "]" } ;
primary     = INT | STRING | "true" | "false" | IDENT
            | "(" expr ")"
            | ifExpr
            | structLit
            | arrayLit ;
structLit   = IDENT "{" [ fieldInit { "," fieldInit } [ "," ] ] "}" ;
fieldInit   = IDENT ":" expr ;
arrayLit    = "[" [ expr { "," expr } [ "," ] ] "]" ;
```

Notes:
- **Assignment targets.** In `expr assignOp expr ";"`, the left-hand side must be a *place*: an identifier, a field access `e.f`, or an index `e[i]`. These can nest (`a[i].kids[j]`). Anything else is the compile error `invalid assignment target`. This replaces v0's `IDENT "=" expr ";"` rule.
- **Struct literals in headers.** The condition of `if`/`while`, and both expressions in a `for` header, are parsed in a *no-struct-literal* mode. There, `IDENT {` is read as an identifier followed by a block. To use a struct literal in a header, put it in parentheses. The mode applies only to the top level of the header expression: `(`, `[`, call arguments and struct literal field values each switch it off again inside them. Without parentheses, `if p == Point { x: 1, y: 2 } { ... }` fails with a parse error. That is acceptable, because `==` on structs is a type error anyway.
- **`for` headers.** In `forStmt`, `expr ".." expr` is a range and a single `expr` is an array. `..` is not an expression operator anywhere else.
- **Calls.** Only a plain identifier can be called, as in v0. `a.f()` and `a[0]()` are type errors.
- **Trailing commas** are allowed in struct declarations, struct literals and array literals. They are still not allowed in parameter lists or call arguments, which keeps those as in v0.

### 3.4 Declarations and name resolution

- Top-level functions and structs may appear in any order. Structs may refer to themselves and to each other.
- Struct names live in the **type namespace**. A struct name must not be `int`, `bool`, `string` or `void`, and must not duplicate another struct, a function or a builtin.
- A local variable may share a struct's name. Struct literals and type positions always resolve in the type namespace.
- Field names must be unique within a struct. They are ordinary identifiers, so `len` and even `int` are valid field names. A field's type must resolve and must not be `void`.
- An empty struct (`struct Unit {}`) is allowed.

### 3.5 Type rules

**Struct literal** `Name { f1: e1, ..., fn: en }`
- `Name` must be a struct.
- Every field must appear exactly once. Errors: `missing field '<f>' in '<Name>'`, `duplicate field '<f>'`, `unknown field '<f>' on '<Name>'`.
- Fields may be listed in any order. They are evaluated in the order written.
- Each `ei` is checked against the declared field type.

**Field access** `e.f`
- `e` must have a struct type with a field `f`.
- Otherwise the error is `unknown field '<f>' on '<T>'`. For a non-struct `e`, the type shown is `e`'s type.

**Index** `e[i]`
- `e` must be an array and `i` an `int`. The result has the element type.
- Indexing a `string` is a type error; `byte_at` remains the way to read string bytes.

**Array literal** `[e1, ..., en]`
- If an *expected type* (below) is an array type `[T]`, every element is checked against `T`.
- Otherwise the first element's type `T` gives the literal type `[T]`, and the remaining elements must match `T`.
- `[]` with no array expected type is the error `cannot infer type of empty array`.

**Expected types.** Bidirectional checking is limited to these positions, each of which has a known type:
- a `let`/`var` initialiser (the declared type)
- the right-hand side of `=` (the place's type)
- a function call argument (the parameter type)
- `return e` (the function's return type)
- a struct literal field value (the field type)
- `push`'s second argument (the array's element type)
- an array literal element (the element type, when the literal itself has an expected type)

The expected type also passes into both branches of an `if` expression and through parentheses. It only affects array literals. Every other expression is checked as in v0, and then compared with the expected type as before.

**Equality.** `==` and `!=` on struct or array operands are the compile error `cannot compare '<T>' values`.

**`print`** still accepts only `int`, `bool` and `string`.

### 3.6 Assignment and compound assignment

- `x = e;` requires `x` to be a `var` (as in v0). Writing through a place (`e.f = v;`, `e[i] = v;`) is always allowed, whatever binding the object was reached through.
- `p op= e;` requires that `p op e` is well typed with the type of `p`:
  - `+=` accepts `int` or `string` (concatenation).
  - `-= *= /= %=` accept `int` only.
  - The same `var` rule applies when `p` is a bare identifier.
- **Evaluation order and single evaluation:**
  - `o.f = v`: evaluate `o`, then `v`, then store.
  - `a[i] = v`: evaluate `a`, then `i`, then `v`, then bounds-check and store.
  - `o.f op= v`: evaluate `o` once, load `o.f`, evaluate `v`, compute, store.
  - `a[i] op= v`: evaluate `a` and `i` once each, bounds-check and load, evaluate `v`, compute, store into the same element.
  - In every case `/=` and `%=` panic on zero exactly as `/` and `%` do.

### 3.7 `for` loops

**`for x in a..b { body }`**
- `a` and `b` must be `int`. Both are evaluated once, `a` first, before the first iteration.
- `x` takes the values `a, a+1, …, b-1`. When `a >= b`, the body runs zero times.
- The hidden counter can never overflow: it only increments after `x < b` holds, so it never exceeds `b`.

**`for x in arr { body }`**
- `arr` must be an array `[T]`, and `x` has type `T`.
- `arr` is evaluated once into a hidden temporary, so reassigning the variable it came from has no effect on the loop.
- A hidden index starts at `0`. Before each iteration the loop checks `index < len(temp)` against the *current* length. Pushing inside the loop therefore extends the iteration, and popping shortens it without going out of bounds.

**Both forms**
- `x` is a new immutable binding scoped to the body. It may shadow an outer name.
- `break` exits the loop. `continue` goes on to the next iteration, through the counter increment.
- Missing-return analysis treats a `for` loop as possibly running zero times. A `for` never terminates a control path on its own.

### 3.8 Builtins

New or extended (special-cased in the checker, as `print` is):

| Builtin | Signature | Behaviour |
|---------|-----------|-----------|
| `len` | `(s: string): int` / `(a: [T]): int` | Byte length of a string, or element count of an array. |
| `push` | `(a: [T], x: T): void` | Appends `x`. `x` is checked with expected type `T`. |
| `pop` | `(a: [T]): T` | Removes and returns the last element. Panics if the array is empty. |

Passing a non-array to `push`/`pop`, or something that is neither a string nor an array to `len`, is a type error naming the builtin and the type found.

### 3.9 Runtime panics

These join v0 §3.6, using the same format and exit code 101:
- Index outside `[0, len)` on read or write: `index out of bounds: index <i>, length <n>`. This is the same message `byte_at` uses.
- `pop` on an empty array: `pop from empty array`.
- Allocation failure for a struct or array: `out of memory`.

## 4. Compiler changes

### 4.1 Structured types (lands first, behaviour-preserving)

`Type` in `check/types.ts` and `IrType` in `ir/ir.ts` are bare string unions today. Both become tagged unions:

```ts
type Type =
  | { kind: 'int' } | { kind: 'bool' } | { kind: 'string' } | { kind: 'void' } | { kind: 'error' }
  | { kind: 'struct'; name: string }
  | { kind: 'array'; elem: Type };
```

The change also adds:
- shared singletons for the primitive types
- `typeEquals(a, b)`
- `typeToString(t)`, which produces `int`, `Point` or `[[int]]`, and is used in every diagnostic that names a type

This commit only changes the representation. It adds no syntax, and the full v0 test suite must pass unchanged. Every later commit builds on it.

### 4.2 Lexer, AST and parser

- Lexer: the new keywords and tokens from §3.1.
- AST:
  - `Program` holds `items` (functions and structs).
  - A `TypeExpr` node is either `{ kind: 'named', name }` or `{ kind: 'array', elem }`, each with a span.
  - New expressions: `field`, `index`, `structLit` and `arrayLit`.
  - The assignment statement becomes `{ kind: 'assign', target: Expr, op: '=' | '+=' | …, value }`, and the checker validates `target` as a place.
  - New statements: `forRange` and `forEach`.
  - The s-expression printer learns every new node.
- Parser:
  - `.` and `[` join call as postfix operators at the same precedence level.
  - A `noStructLit` flag is threaded through expression parsing, set for `if`/`while`/`for` headers and cleared inside brackets (§3.3).
  - Error recovery also synchronises at `struct`.

### 4.3 Checker

- **Pass 1:** collect struct declarations and function signatures. That covers duplicate and colliding names and unknown types, and each struct's field table.
- **Pass 2:** check function bodies. `checkExpr(expr, expected?)` takes the optional expected type from §3.5.
- **Places:** a separate `checkPlace(expr)` returns a typed place:
  - `{ kind: 'local' }`, `{ kind: 'field' }` or `{ kind: 'index' }`
  - It applies the `var` rule only to bare locals.
- **Typed tree:**
  - `TypedProgram` gains `structs` (name and ordered, typed fields).
  - New expressions: `field`, `index`, `structLit` (initialisers kept in *written* order, each tagged with its field) and `arrayLit`.
  - New statements: `assign` with a typed place and an op, `forRange`, `forEach`.
  - `push`/`pop`/`len` are `builtin` nodes with an array-or-string variant recorded.
- **Error cascades:** the `error` type still suppresses follow-on diagnostics, including through field and index access on `error`-typed operands.

### 4.4 IR and lowering

`IrProgram` gains `structs: { name; fields: { name; type }[] }[]`. The IR stays non-SSA. These instructions are new:

| Instruction | Meaning |
|-------------|---------|
| `struct_new dst, Name, [operands]` | Allocate and initialise every field. Operands are in declaration order, and lowering has already evaluated them in written order into temporaries. |
| `field_get dst, obj, field` | Load a field. |
| `field_set obj, field, value` | Store a field. |
| `array_new dst, elemType, [operands]` | Allocate with the given elements. |
| `index_get dst, arr, idx` | Bounds-checked load. |
| `index_set arr, idx, value` | Bounds-checked store. |
| `array_len dst, arr` | Element count. |
| `array_push arr, value` | Append. |
| `array_pop dst, arr` | Remove the last element. Panics when the array is empty. |

v0's string `len` builtin keeps its existing `call_builtin` form. Array `len` lowers to `array_len`.

Lowering:
- **Compound assignment.** Evaluate the place's object (and index) into temporaries once, then emit get, `binop`, set. A bare-local target uses `binop` straight into the local.
- **`forRange`.** Evaluate `a` and `b` into a hidden counter and a hidden limit, then emit blocks `header` (`br counter < limit`), `body` (copy counter into `x`), `step` (counter += 1, `jmp header`) and `exit`. `continue` jumps to `step`.
- **`forEach`.** Evaluate the array into a temporary, then use the same block shape with a hidden index. `header` checks `index < array_len(temp)`, and `body` starts with `x = index_get temp, index`.
- The IR printer prints every new instruction, for `--emit=ir` and snapshots.

These map directly onto LLVM IR later (`getelementptr` + `load`/`store`, and runtime calls for arrays).

### 4.5 C backend and runtime

**Mangling** (added to v0 §4.4):
- A struct type `Name` becomes the C type `aster_S_Name`.
- A field `f` becomes `f_f`. Field names therefore never collide with C keywords: `int` becomes `f_int`.

**Structs**
- Each struct is emitted as a pointer typedef plus a definition:
  ```c
  typedef struct aster_S_Point *aster_S_Point;   /* all typedefs first */
  struct aster_S_Point { int64_t f_x; int64_t f_y; };
  ```
- All typedefs come before any definition, so recursive and mutually recursive structs compile.
- `struct_new` emits `aster_rt_alloc(sizeof(struct aster_S_Name))` followed by field stores.

**Arrays.** One runtime type, so no C is generated per element type:
```c
typedef struct { int64_t len; int64_t cap; int64_t elem_size; void *data; } aster_array;
aster_array *aster_rt_array_new(int64_t elem_size, int64_t len);  /* len zeroed slots */
void *aster_rt_array_at(aster_array *a, int64_t i);               /* bounds-checked slot pointer */
void *aster_rt_array_push_slot(aster_array *a);                   /* grows (doubling), returns new slot */
void *aster_rt_array_pop_slot(aster_array *a);                    /* panics if empty; slot stays valid */
```
The emitter writes typed access through casts, for example `*(int64_t *)aster_rt_array_at(l3, l4) = l5;`. `array_new` emits `aster_rt_array_new(sizeof(T), n)` followed by one store per element. An array-typed value is `aster_array *`.

**Allocation.** `void *aster_rt_alloc(int64_t size)` uses `malloc` and panics with `out of memory` on failure. Array growth uses the same failure path.

Generated C must stay clean under `-std=c11 -Wall`, and the golden suite still adds `-Werror`.

### 4.6 Unchanged

Diagnostic formatting, the cc invocation in the driver, the CLI commands and exit codes, and the golden-test directive format all stay as they are. `--emit=tokens|ast|ir|c` simply shows the new constructs.

## 5. Testing

### 5.1 Golden programs

New feature folders under `tests/programs/`:

- `structs/`
  - literals with fields in any order
  - evaluation order of field initialisers, shown with prints
  - field get and set, including through a `let` binding
  - aliasing: a write through one reference is visible through another
  - structs passed to and returned from functions
  - recursive and mutual struct types, used via arrays
  - structs declared after their use
  - an empty struct
- `arrays/`
  - literals and nested arrays
  - `[]` in every expected-type position from §3.5, including `if`-expression branches
  - index get and set
  - `push`/`pop`/`len`
  - aliasing
  - arrays of structs, and structs containing arrays
- `loops/`
  - range loops, including empty and negative ranges
  - range bounds evaluated once (a printing side effect)
  - `for x in arr`, including pushing and popping during iteration
  - `break`/`continue` in both forms
  - shadowing by the loop variable
  - a function whose only path out goes through a `for` is a missing-return error (this lives under `errors/`)
- `compound/`
  - every operator on locals, fields and elements
  - string `+=`
  - single evaluation of `a[next()] += 1` (a printing side effect)
  - `/=` by zero panics (this lives under `panics/`)

Additions to `errors/`:
- `invalid assignment target`
- assigning to a `let` local, including with `+=`
- unknown struct type, unknown field, missing field, duplicate field in a literal, duplicate field in a declaration
- a struct name that collides with a function, a builtin or a primitive type
- `[void]` and a `void` field
- `cannot infer type of empty array`
- array element type mismatch
- `cannot compare` on structs and on arrays
- indexing a string or an `int`
- calling a field
- `push`/`pop`/`len` on the wrong type
- `print` of a struct
- a struct literal in an `if` header without parentheses (parse error)
- `for` over a non-array, and a range with non-`int` bounds

Additions to `panics/`:
- index out of bounds on read
- index out of bounds on write
- negative index
- `pop` on an empty array
- `/=` by zero

Real programs, in `programs/`: `tokenizer_structs.aster` and `rpn.aster` (§1).

### 5.2 Unit tests

These stay lean, as in v0:
- Lexer: the new tokens, and `1..5` lexing as three tokens.
- Parser snapshots:
  - postfix chains (`a[i].kids[j]`, `f(x).y`)
  - the no-struct-literal rule in each header kind, and that it lifts inside parentheses
  - every assignment op
  - both `for` forms
  - recovery at `struct`
- Checker:
  - expected-type inference for `[]` (each position, plus nested `[[]]`)
  - place mutability rules
  - error-cascade suppression through `.`/`[]`
- Lowering snapshots:
  - single evaluation in compound assignment on a field and on an element
  - `forRange` and `forEach` block shapes, with `continue` going to `step`
- Emitter: struct typedef ordering for mutually recursive structs, and the array access casts.

### 5.3 Workflow

As in v0: TDD with a failing golden program or unit test first, conventional commits, and CI running typecheck, lint and test. The §4.1 refactor commit comes first and must change no tests.

## 6. Looking ahead (informing, not in scope)

- **v0.2** adds `enum` with payloads and `match`. The structured `Type` union gains `{ kind: 'enum' }`, and enum values are heap references like structs. With `match`, optional values become expressible without null (per-type enums, since there are still no generics).
- **v0.3** adds reading files and stdin into `string`, and program arguments as `[string]`.
- **Then:** an LLVM emitter over the same IR, and porting `asterc` to Aster.
