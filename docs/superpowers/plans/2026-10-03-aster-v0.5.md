# Aster v0.5: Generic Enums and `?` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add user-declared generic enums (with `Option[T]` and `Result[T, E]` predeclared), the postfix `?` operator, `read_file` returning `Result[string, string]`, then dogfood all of it by rewriting `parse.aster` without its `failed` flag and placeholders.

**Architecture:** Generic enums are monomorphised in the checker. A generic enum is kept as a *template* (its `EnumDecl` and parameter names). Each distinct instantiation such as `Option[int]` becomes an ordinary `TEnum` whose `name` is the type string `Option[int]`, registered in `env.enums` under that string. Lowering and the IR therefore don't change, and the C backend only gains a mangling for names containing `[`. `?` checks to a new `try` typed expression, which lowers to a tag test, a branch and an early `ret` of a freshly built `None`/`Err`.

**Tech Stack:** TypeScript (Node 24, pnpm, vitest, oxlint), C11 runtime compiled with the system `cc`. The self-hosted programs are Aster.

**Spec:** `docs/superpowers/specs/2026-10-03-aster-v0.5-design.md` (read it first; this plan argues from it).

## Global Constraints

- Generated C and the runtime must compile cleanly under `-std=c11 -Wall -Werror`.
- Existing golden programs and unit tests keep passing. The only existing expectations allowed to change are the ones
  that mention `ReadResult` (Task 5), and `parse.aster`'s internals (Task 7; its output must not change).
- Exact messages (copy verbatim):
  - `duplicate type parameter '<T>'`
  - `type parameter '<T>' conflicts with a type of the same name`
  - `type parameter '<T>' is never used`
  - `generic enum '<E>' expands infinitely`
  - `'<E>' expects <n> type argument, got <m>` when n is 1, and `'<E>' expects <n> type arguments, got <m>` otherwise
  - `'<Name>' is not generic`
  - `type argument cannot be void`
  - `cannot infer type arguments for '<E>'`
  - `'?' applies to Option or Result, not '<T>'`
  - `'?' needs the function to return an Option, but it returns '<T>'`
  - `'?' needs the function to return a Result, but it returns '<T>'`
  - `'?' error type '<E1>' does not match the function's error type '<E2>'`
  - `'<name>' is a builtin type and cannot be redefined` (existing `builtinTypeMessage`, now for `Option`/`Result`)
  - `unknown type '<T>'` (existing)
- Diagnostics write types with `typeToString`. An instantiation prints as `Name[a, b]`, with `, ` between arguments.
- C names: a non-generic enum stays `aster_E_<name>`. An enum whose name contains `[` is `aster_G_` followed by the name
  with `_`→`__`, `[`→`_L`, `]`→`_R` and `, `→`_C`, applied left to right in a single pass over the characters.

## Review Focus

1. **Recursive instantiation terminating.** `enum List[T] { Cons(T, List[T]), Nil }` used as `List[int]` must
   instantiate once, with the TEnum registered before its payloads are resolved. Pinned by `generics/list.aster` in Task 4.
2. **The same instantiation reached by different routes** (a struct field, a function parameter, an inferred variant)
   must be one `TEnum` and one C type, so values flow between them. Pinned by `generics/shared_instance.aster` in Task 4.
3. **C name collisions.** `enum A_L { X(int) }` next to `A[…]` (and `My_E` as a type argument) must produce distinct C
   names. Pinned by `generics/c_names.aster` in Task 4, and by a unit test of `mangleEnum` in Task 4.
4. **`?` failure path skipping later side effects.** In `f(a()?, b())` the call `b()` must not run when `a()` is `None`.
   Pinned by `try/order.aster` in Task 6.
5. **Errors in an unused generic enum, reported exactly once.** A template is validated once with placeholders, and
   instantiations resolve silently. Pinned by `errors/generic_decls.aster` in Task 3, which also uses the enum twice,
   so the error must still appear only once.

**Interfaces:**
- Produces:
  - `type.ts`: the enum case becomes `{ kind: 'enum'; name: string; generic?: { base: string; args: Type[] } }`. For an
    instantiation, `name` is the full type string (`Option[int]`) and `generic` holds the base name and arguments. A
    non-generic enum has no `generic`, so existing `{ kind: 'enum', name }` literals stay valid.
  - `typeEquals` stays name-based. The type string is injective, so names are enough.
  - `typeToString` returns `name` for enums, which already holds `Option[int]`.
  - `instanceName(base: string, args: Type[]): string`, which returns `${base}[${args.map(typeToString).join(', ')}]`.
  - `builtins.ts`: `export const OPTION = 'Option'`, `export const RESULT = 'Result'`, and
    `export const PRELUDE_SOURCE = 'enum Option[T] { Some(T), None }\nenum Result[T, E] { Ok(T), Err(E) }\n'`.
  - `generics.ts`:
    - `interface Template { decl: EnumDecl; params: string[]; broken: boolean }`. `broken` is set when the expansion
      check rejected the enum, or the declaration was rejected outright. A broken template resolves to `ERROR` without
      instantiating.
    - `function findExpandingEnums(templates: ReadonlyMap<string, Template>): Set<string>` implements spec §3.3's graph
      check and returns the names of the enums to report.
  - `checker.ts`:
    - `Env` gains `templates: Map<string, Template>` and `instances: TEnum[]` (instantiations in first-use order).
    - `resolveType(env, ref, bindings?: ReadonlyMap<string, Type>, quiet?: boolean): Type`. `bindings` maps type
      parameter names to types, and `quiet` suppresses diagnostics.
    - `instantiate(env, template, args: Type[]): Type` returns the instantiation's `Type`, creating, registering and
      filling its `TEnum` on first use. Task 4 relies on it.
